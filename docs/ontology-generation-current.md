# 本体建设、全局汇总与查数后召回

本文整理 Datrix 当前本体的构成、生成流程、场景级与全局本体的关系，以及查询结果返回后的召回方式。文中区分了当前实现和仍待完善的设计点。

## 1. 本体在本项目中的职责

Datrix 按场景查数。场景路由、字段选择和 SQL 生成仍由场景配置及查询 Agent 完成；本体不参与 SQL 规划。本体的职责发生在数据已经查出之后：帮助主 Agent 识别结果中的业务概念、理解指标口径、解释异常，并判断不同场景的结果是否能放在一起比较。

可以把职责概括为：

> 查询结果提供本轮事实，本体提供解释这些事实所需的业务语义和分析约束。

因此，建设本体时要回答：结果列代表什么、指标口径是什么、适用哪些分析维度、有什么解释限制，以及跨场景比较需要什么条件。

## 2. 本体的组成与项目里的三层视角

一般本体可用类/概念、属性/关系、公理/约束和个体/实例来描述领域知识。本项目关注查数后的分析，不需要把每类 OWL 构件都照搬进来，也不需要把查询结果中的每一行都复制成长期保存的个体。

在本项目中，更实用的是按三层理解本体内容：

| 逻辑层 | 回答的问题 | 当前可对应的内容 |
| --- | --- | --- |
| 业务语义层 | 业务对象和指标是什么？ | 实体、实体关系、指标名称与口径、单位、时间依据、统计粒度 |
| 分析解释层 | 查到结果后如何解释？ | 指标含义、常见异常、推荐分析维度、结果分析规则、澄清规则、跨场景分析约束 |
| 映射治理层 | 本体概念对应哪些场景数据？依据是否可信？ | 场景绑定、语义键、结果列匹配信息、来源证据、场景快照和审核状态 |

这三层目前是**逻辑上的分类**，不是三套独立存储或三个服务。现有场景抽取和全局汇总结构没有正式按三层分区；映射信息、证据和生命周期状态仍分布在多个字段和流程中。

## 3. 原材料和指标来源边界

每个场景提供语义文档和数据字典。语义文档包括场景 Markdown 中的结构化配置（如 `metrics`）以及业务语义正文；数据字典说明物理字段、业务名称、类型、单位等。

本项目对指标来源采用以下约束：

- 本体指标必须在语义文档中明确声明或描述。
- 不根据数据字典中的字段名、字段类型或字段说明猜测指标。
- 不自动从两个指标推导比例、差值、合计等新指标。
- LLM 提取的指标必须提供语义文档证据，指标名称也必须能在业务语义正文或结构化 `metrics` 定义中找到；否则校验失败。
- 数据字典可以为已经声明的指标补充字段映射和属性，例如语义键、单位、粒度和时间依据；它不负责定义新的业务指标。
- 查询能力只辅助结果列绑定，不作为新增本体指标的来源。

例如，语义文档明确写了“合同金额”和“已支付金额”，本体可以提取这两个指标。如果文档没有定义“支付率”，系统不能仅凭这两个指标自动新增支付率。

## 4. 场景级本体包含什么

LLM 模式会为每个场景单独生成一个中间抽取结构 `SceneOntologyExtraction`，包含：

- 场景标识、领域标识和场景名称；
- 实体候选及其别名、定义、业务角色和证据；
- 指标候选及单位、聚合方式、统计粒度、时间依据、公式、所属实体、语义键、分析含义、解读、异常、推荐维度和证据；
- 场景内实体关系及其证据；
- 分析能力，包括适合的问题、推荐指标和维度、注意事项；
- 候选关联键、澄清规则和质量提醒。

它是一份**单场景的候选抽取结果**，结构上并没有拆成业务语义层、分析解释层和映射治理层。实体和关系主要对应业务语义；指标解释、分析能力和澄清规则对应分析解释；语义键、关联键和证据与映射治理有关，但目前没有一个完整独立的映射治理对象。

规则模式不会生成这份独立的 `SceneOntologyExtraction` JSON。它直接读取各场景材料并构建草稿；其中指标只读取语义文档结构化配置里的 `metrics`。只写在业务语义正文中的指标，规则模式目前不会抽取；LLM 模式可以提取正文中明确描述的指标。

## 5. 全局本体如何生成

### LLM 模式

LLM 模式分两阶段：

1. **逐场景抽取**：每个场景分别生成上述场景级本体 JSON。
2. **全局汇总**：第二次 LLM 调用接收各场景抽取 JSON，整理成全局本体，包括全局实体、指标、实体关系、指标关系、分析维度、跨场景分析路径、结果分析规则、澄清规则和未解决问题。

全局汇总会尝试归并同义概念和指标，但要求保留领域边界；不同领域的同名概念不能仅凭名称合并。跨场景关系先以候选状态表达，描述业务映射依据、关联键、时间和粒度条件、允许的分析及禁止的推断。它是查数后的分析契约，不是 SQL JOIN。

汇总后，系统检查场景与对象引用、领域命名空间、指标名称和证据。全局生成提示要求指标只能来自场景级抽取；校验器还检查指标名称和证据是否有语义文档依据。不过，当前尚未严格校验“每个全局指标必须对应一个或多个场景级指标 ID”，这是全局追溯上的缺口。

### 规则模式

规则模式不经过“场景级 JSON → 全局汇总”这条链路，而是直接从场景材料确定性地生成草稿。实体候选仍可能按场景名称、业务语义和字段描述中的已知业务词匹配；指标则不再使用字段关键词推测，只从结构化语义配置中读取。规则模式适合生成基础草稿，无法像 LLM 模式那样完整抽取正文中的分析解释。

## 6. 场景级本体和全局本体是否同构

两者不是相同结构的简单复制。

| 场景级抽取 | 全局汇总 |
| --- | --- |
| 单场景本地实体、指标和关系 | 带领域命名空间的全局实体、指标和关系 |
| 单场景分析能力、候选关联键和澄清规则 | 全局分析维度、指标关系、结果分析规则和跨场景路径 |
| 证据指向当前场景 | 对象记录来源场景，绑定指向场景语义键 |

全局本体会对场景级信息进行归并和组织，并增加跨场景分析内容。它仍不是一份已经按三层正式建模的本体。

## 7. 草稿、编译和发布

生成入口读取当前活动场景快照。生成后的本体 Markdown 保存为草稿，不会直接替换活动本体。编译器把 Markdown 转成 `OntologyGraph` 和供运行时召回的投影结构，并检查表格格式、对象引用、场景绑定和跨场景契约等内容。通过校验后，发布流程会把编译图与活动场景片段合并成不可变的本体快照；场景片段只允许加入语义配置中明确声明的指标，通用查询能力生成的聚合项不会变成本体指标。管理员激活快照后，运行时才会使用它。

整体流程如下：

```text
活动场景快照及场景文档
        │
        ├─ LLM：场景级抽取 → 全局汇总
        └─ 规则：直接读取场景材料生成草稿
                    │
                    ▼
          指标来源及对象引用校验
                    │
                    ▼
             Markdown 草稿
                    │
                    ▼
       编译为图结构并检查完整性
                    │
                    ▼
             管理员审核发布
                    │
                    ▼
         活动本体快照供运行时使用
```

## 8. 查数后的本体召回

查询和 SQL 执行结束后，系统才调用本体分析服务。召回入口结合当前场景、结果列及其语义键、单位、类型、聚合和时间/粒度信息，选择相关实体、指标、分析规则及跨场景关系，交给主 Agent 解释结果。召回不会回到 SQL 规划阶段，也不会自动发起跨场景 JOIN。

没有匹配到的结果列会保留为未绑定信息。跨场景候选关系不会直接当作已确认规则使用；已确认桥接也需要满足场景范围、权限及两侧结果的时间和业务粒度对齐条件。

## 9. 当前差距和后续重点

当前已具备场景级抽取、全局汇总、本体编译发布和查数后召回的基础链路，也已禁止从字段关键词自动生成指标。与三层目标相比，仍有这些差距：

1. 三层内容未在数据模型和生命周期中显式分开。
2. 全局指标缺少指向场景级指标 ID 的强制来源追溯。
3. 规则模式只识别结构化指标配置，不解析业务语义正文中的指标定义。
4. 映射、证据、版本和审核状态尚未统一为完整的治理记录。

后续完善时，可以先保持一个本体快照和现有服务边界，在快照内部明确三层对象；补充全局到场景级指标的强制追溯，并统一保存字段映射、证据、来源版本和审核状态。这样不需要改变“先查数、后召回本体分析”的流程。
