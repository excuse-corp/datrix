# AskData 场景权限与本体隔离优化方案

## 目标

让用户管理页中的 `scene_ids` 成为 AskData 主聊天、场景 API 和本体上下文共同遵循的权限来源，避免出现“用户只获准访问部分场景，但问数路由或本体仍使用全局信息”的情况。

一期继续使用一份全局发布本体，不为每个用户复制和维护一份本体。查询时以用户可访问的场景为边界，动态生成只含授权场景语义的本体上下文。

## 当前实现与问题

- `AskDataPrincipal.can_access_scene()` 将 `admin` 和 `ask_data_admin` 都视为全场景管理员；普通用户依赖 `scene_ids`。这使问数管理员也能绕过场景授权。
- AskData API 从认证中间件的 `request.state.user` 构造身份时会读取 `scene_ids`；但主聊天路径在 `agentic_data_api.py` 中只将 `user_token.role` 传给 `AskDataPrincipal`，没有场景授权列表。于是角色和场景规则在不同入口表现不一致。
- 本体是全局单一草稿和活动快照。场景语义文档被合并进该本体；本体图谱接口会按用户可访问场景筛选来源，但普通本体读取接口仍返回共享草稿/快照元数据。
- 问数结果本体投影使用实际查询场景作为相关性条件，但 `relevant_ontology_projection()` 目前主要用场景信息加权排序，并未保证每个来源于未授权场景的节点和边都被硬性移除。

## 权限规则

统一采用以下规则：

| 角色 | AskData 场景访问 | 场景管理 | 全局本体管理 |
| --- | --- | --- | --- |
| `admin` | 所有已发布场景 | 是 | 是 |
| `ask_data_admin` | 仅用户 `scene_ids` 中的场景 | 是 | 是 |
| `normal` | 仅用户 `scene_ids` 中的场景 | 否 | 否 |

平台管理员的全场景权限是明确的全局授权。问数管理员负责管理场景和本体，但执行业务问数时仍按 `scene_ids` 控制。场景管理操作仍由 `ask_data_admin` 和 `admin` 使用。

CAS 用户继续映射到内部用户记录；场景权限从内部用户记录读取，不从 CAS 属性或请求头接受授权值。

## 实施设计

### 1. 统一认证主体

- 增加单一 Principal 构造入口，将 `request.state.user` 中的 `user_id`、完整角色集合和 `scene_ids` 转换为 `AskDataPrincipal`。
- AskData HTTP API 和主聊天请求都使用这个构造入口。主聊天路由把认证主体传到 ReAct AskData 工具，不再从 `UserRequest.role` 单独猜测授权。
- 认证中间件启用时，若 `request.state.user` 缺失，不允许由 `X-User-Id`、`X-AskData-Role`、`X-AskData-Scenes` 头创建生产身份。保留现有头部回退仅供明确启用的集成/测试模式。
- 角色以集合比较，不依赖 `AuthUser.role` 返回的第一个角色；同时保留用户 ID 和场景列表的规范化。

### 2. 明确角色能力与后端强制校验

- 将“可管理 AskData”与“可访问全部场景”拆成两个判断：`is_platform_admin`、`can_manage_ask_data`、`can_access_scene(scene_id)`。
- `admin` 的 `can_access_scene` 始终允许；其他角色必须命中 `scene_ids`。`ask_data_admin` 只获得管理操作权限，不自动扩大查询范围。
- 场景列表、能力列表、场景查询、计划任务、查询详情/结果和澄清续问均在后端执行权限检查。不能只过滤前端选项或依赖 Agent 遵守提示。
- 路由 Agent 返回计划后，对每个 `scene_id` 再校验一次；未授权或不存在的场景统一按不可见处理，避免泄露场景是否存在。
- 查询记录继续绑定用户 ID。管理员可按现行管理策略查看；问数管理员不能仅因管理角色读取其他用户的私有查询记录。

### 3. 保持全局本体，按授权场景生成运行时视图

- 继续由管理员编辑、验证和发布一份全局本体；这避免每个用户拥有不同版本造成维护、发布和审计复杂度。
- 场景文档生成的实体、指标、关系和分析规则保留来源 `scene_id`。构造运行时本体上下文时，先硬过滤来源集合与 Principal 授权场景不相交的项目，再做问题相关性排序和节点数量裁剪。
- 对多个来源场景合并的本体条目，只有当其全部来源都在授权集合内时才对用户可见；平台管理员可见全部条目。
- 手工编写、没有场景来源的全局条目需有明确可见性规则。默认只向管理员展示；如需普通用户使用，应显式标记为全体用户可见，并避免引用未授权场景的名称、字段或指标。
- 查询结果构造器接收 Principal 的授权场景集合，而不是仅接收本轮碰巧命中的查询场景；其上下文同时要求来源授权和本轮结果相关。无授权场景时不提供本体内容。
- 本体图谱、来源清单和快照读取接口按同一规则返回授权视图。共享草稿 Markdown、全量修订记录和包含其他场景来源的快照元数据只对本体管理员开放。

### 4. 查询结果与缓存边界

- 查询计划、SQL 生成、执行和结果回传都以同一个 Principal 为准，执行前后检查场景权限，防止权限在计划生成与执行间变化时继续访问。
- 澄清续问恢复查询时重新读取当前认证主体及权限，不能只信任进程内待办对象保存的旧权限。
- 成功结果缓存键包含用户 ID、已授权场景集合版本或 `authz_version`；场景授权变化后旧缓存不可复用。
- 本体上下文、查询结果和审计记录保留使用的场景 ID 与活动本体快照 ID，方便解释“用户当时依据哪些数据和口径得到结果”。

## 修改范围

- `packages/dbgpt-app/src/dbgpt_app/scene/ask_data/security.py`：拆分管理权限和全场景访问权限。
- `packages/dbgpt-app/src/dbgpt_app/scene/ask_data/api/scenes.py`：统一 Principal 来源，覆盖场景、查询、续问及管理员边界。
- `packages/dbgpt-app/src/dbgpt_app/openapi/api_v1/agentic_data_api.py`、`openapi/api_v1/tools/ask_data.py`：将完整 Principal 贯穿主聊天 AskData 工具链。
- `packages/dbgpt-app/src/dbgpt_app/scene/ask_data/api/ontology.py`、`ontology/context.py`、`result/builder.py`：本体接口授权和运行时来源硬过滤。
- 相邻认证、AskData 安全、本体 API 和结果构造测试；更新用户管理/AskData 技术说明与交接文档。

## 实施步骤

1. 更新 Principal 能力方法和角色规则，补充角色矩阵的最小单元测试。
2. 从认证主体创建统一 Principal，并接入主聊天与澄清续问；验证普通用户确实只发现获准场景。
3. 在场景执行计划入口和执行边界再次检查 `scene_ids`，检查查询历史的用户隔离。
4. 给本体图节点和投影加入来源过滤；先硬过滤再排序，并限制全局草稿、修订、快照的可见范围。
5. 为缓存加入授权版本边界，更新相关说明。
6. 运行必要的 AskData 权限、本体过滤及主聊天工具专项测试，编译改动 Python 文件；前端有变化时只运行对应 ESLint/静态构建。不跑无关的全量测试。

## 验收标准

- 普通用户和 `ask_data_admin` 只看到并能执行其 `scene_ids` 授权的场景；构造未授权场景计划时后端拒绝。
- `admin` 可访问所有已发布场景。
- `ask_data_admin` 可管理场景和全局本体，但不能据此跨场景问数或查看他人私有查询记录。
- 不同授权用户通过运行时图谱/本体上下文拿到不同的场景语义视图；未授权来源的节点、边、名称和指标不能进入上下文。
- 用户读取本体不会得到未经授权的共享草稿、修订内容或完整来源清单。
- 认证主体缺失或过期时 AskData 主聊天不回退到由客户端请求头提供的身份。
- 权限变更后，后续查询、澄清续问和缓存读取均按新权限执行。

## 风险与取舍

- 全局本体中的手工规则可能有跨场景业务含义。当前采用保守规则：无场景来源的全局条目只供问数管理员管理使用，不进入普通用户的图谱和问数上下文；如后续需要共享给普通用户，应为条目增加明确的全局可见标记。
- 条目拥有多个场景来源时采用“全部来源均授权才可见”的保守策略，可能使部分共享指标对某些用户不可见，但不会通过共享定义泄露未授权业务信息。
- 全局本体仍由管理员统一发布；用户差异发生在读取和查询时的本体投影，不产生独立本体版本或用户专属编辑流程。
