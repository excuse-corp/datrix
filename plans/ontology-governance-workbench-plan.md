# 本体治理工作台优化升级方案

## 1. 目标

将现有“本体编辑页”升级为围绕生成、核对、审核、发布和追溯的治理工作台，并重点升级本体图谱的视觉表达和探索体验。让工作台清楚呈现本体层次、关系和来源，同时延续 Datrix 的产品界面语言；只有经过审核且来源未过期的版本才能成为运行时活动快照。

核心目标：

- 降低人工审核成本：从 Markdown 全文阅读转为按对象类型和风险处理待办。
- 提升图谱的辨识度与质感：用有层次、可聚焦、能解释来源的画布呈现业务关系，避免关系线堆叠成难读的“毛线团”。
- 保持产品一致性：图谱的控件、颜色、圆角、阴影和明暗主题跟随 Datrix 当前界面主题，不另起一套视觉系统。
- 提高生成结果可信度：指标、映射和跨场景关系都能回到来源场景、版本和证据。
- 让发布状态可解释：区分编译正确、业务审核通过和版本已发布。
- 保证过程可追溯：记录谁在何时对哪个版本/对象做了什么决定，以及决定依据。
- 延续当前运行时边界：本体仍服务于查数后的业务解释，不参与 SQL 生成，也不自动执行跨场景 JOIN。

## 2. 当前基础与问题

当前已有全局本体生成、Markdown 草稿、图谱预览、差异查看、编译检查、版本列表、Neo4j 快照同步和发布能力。生成结果先进入草稿；发布时会校验来源场景快照。跨场景分析路径支持候选、确认和驳回，确认时会检查关联键、时间/粒度条件、允许/禁止分析及证据。

现有图谱基于 React Flow，已经支持按节点类型/场景筛选、搜索定位、缩放、全屏、手动拖动保存布局、迷你地图和节点/关系详情面板。当前默认按类型列出节点，卡片和连线采用基础色标；尚缺少三层/领域聚类、拥挤图折叠、来源链路突出、审核状态可视表达和对 dashboard/明暗主题的完整适配。

主要缺口：

1. Markdown 是编辑入口，实体、指标、规则和映射缺少面向业务人员的独立表单与筛选视图。
2. 证据虽然在部分指标和桥接结构中存在，但工作台没有统一的证据查看、引用定位和来源版本对照体验。
3. 桥接状态主要写入 Markdown；其他对象没有统一的审核动作、审核意见和审核历史。
4. “编译通过”容易被理解为“业务正确”。技术校验与人工审核需要分开呈现和强制执行。
5. 生成和编辑可能更新当前草稿版本；需要在生成前展示影响，并保留可恢复的基线，避免覆盖已有人工修订。
6. 当前管理 API 使用 `can_manage_ask_data` 管理权限，缺少针对审核和发布的记录与发布门禁。首期可以复用 `admin` / `ask_data_admin` 权限，不先引入通用 RBAC。
7. 现有图谱已经有基本探索控件，但布局与卡片信息密度较单一；大图缺少聚类和逐层展开，跨场景桥接、审核状态、来源证据不够突出。

当前关键实现位于 `web/pages/ontology/index.tsx`、`web/utils/ontology.ts`、`packages/dbgpt-app/src/dbgpt_app/scene/ask_data/api/ontology.py`、`packages/dbgpt-app/src/dbgpt_app/scene/ask_data/ontology/service.py` 和 `repository.py`。

## 3. 产品范围

### 本期包含

- 工作台总览：草稿、审核、发布状态、来源变更、编译问题和待办数量。
- 结构化浏览与编辑：实体、指标、分析规则、场景绑定、跨场景路径按类型查看；保留 Markdown 高级编辑入口。
- 证据与来源：展示原始证据、来源场景、语义文档版本/哈希、章节或定位信息；来源缺失和版本失效要醒目标出。
- 审核队列：逐对象确认、驳回修改或不纳入本体，填写审核意见；“驳回修改”保留对象并阻塞发布，“不纳入本体”从当前草稿删除对象及关联引用。提供批量审核，但高风险对象必须逐项查看证据。
- 版本差异：展示对象级新增、修改、删除和来源变更，并支持打开原始 Markdown Diff。
- 发布中心：展示发布检查、审核结论、版本影响、Neo4j 同步状态和回退目标。
- 持久化审核事件和服务端发布门禁。

### 本期不包含

- OWL/RDF 编辑器、通用本体建模器或任意自定义对象类型。
- 从本体直接生成 SQL、JOIN 或改变 AskData 查询规划。
- 新建用户体系或通用 RBAC。保留现有管理角色；四眼审核作为可配置发布规则。
- 将 Neo4j 变成草稿编辑的主存储。关系型元数据库仍是版本、审核和发布管理源，Neo4j 仍是发布图投影。

## 4. 目标工作流

```text
选择活动场景快照
  → 生成预览（模式、来源版本、对象计数、警告、与现稿差异）
  → 创建独立草稿修订（保留上一修订）
  → 技术检查（结构、引用、证据、来源版本、跨场景契约）
  → 对象审核（查看证据；确认、驳回或退回修改）
  → 修订级审核通过（绑定内容哈希和来源快照）
  → 发布检查与影响确认
  → 构建不可变快照、同步并校验 Neo4j
  → 激活快照并保留回退入口
```

任何本体内容变更、来源场景快照变化或编译器影响发布图的版本升级，都会使相应审核失效。审核通过只对审核时的内容哈希和来源快照组合有效。前端按钮状态只是提示，API 服务必须执行所有状态转换和发布门禁。

## 5. 工作台信息架构

### 5.1 总览

首屏显示：当前活动版本、最新草稿、草稿是否落后于活动场景、待审核对象、阻断问题、上次生成模式和结果摘要、Neo4j 健康/同步状态。将“继续审核”“查看来源变更”“发布检查”作为明确待办入口。

### 5.2 本体浏览器

按业务语义、分析解释、映射治理分层；每层提供表格列表、搜索、类型/状态/来源筛选和图谱联动。列表重点展示名称、类型、审核状态、来源数量、最近修改人和修改时间。点选对象后在侧栏查看属性、关系、证据、来源版本和审核历史。

指标优先展示定义、单位、聚合方式、粒度、时间依据、关联实体、来源指标和语义证据。结果绑定展示场景快照、语义键、目标对象、字段映射依据和匹配状态。跨场景路径展示双方场景、关联键、关系类型、时间/粒度契约、允许分析、禁止推断和证据。

### 5.3 对象编辑

常见字段用表单编辑，并提供 Markdown 高级模式。表单保存后仍通过现有编译器生成统一 `OntologyGraph` 和兼容运行时投影；不能让表单写入路径绕过编译、引用检查和状态规则。对象 ID 保持稳定，改名不应生成新对象或丢失关系。

### 5.4 审核队列

按风险排序并解释原因：来源缺失/过期、指标定义无证据、绑定未确认、跨场景契约不完整、对象引用冲突、生成后人工修改等。审核动作可针对单个对象，也可对低风险同类对象批量处理。批量操作必须显示选中数量和对象摘要，并写入逐对象事件。

### 5.5 本体图谱：重点体验设计

图谱应成为可探索的“业务语义地图”，既有视觉吸引力，也要让用户迅速看懂对象、层次、关系、审核状态和来源。

#### 视觉方向

- 沿用 Datrix 的工作区结构：图谱放在现有卡片/面板体系内，沿用 Ant Design 控件、项目圆角和细边框；工具栏和详情侧栏的密度与现有管理页一致。
- 图谱画布使用轻量的技术感底纹：浅色主题用低对比度点阵/网格和蓝青色柔和渐变，深色主题用石墨底色和低亮度青蓝光晕。背景只做衬托，不能压过节点文本。
- 主图采用克制的 2.5D 空间感：画布有轻微轴测视角和远近层次，三层本体像悬浮在同一空间中的半透明图层面板；面板边缘、柔和投影和环境光区分纵深，节点卡片略微浮起，跨层关系用有高度感的弧线连接。
- 空间纵深主要用于表达三层本体和关系路径，名称、指标口径、审核状态和证据仍保持正向、清晰、易读。提供“空间视图/平面视图”切换；平面视图用于密集编辑、精确对照和低动效偏好。
- 不默认自动旋转或持续漂浮。切换视图、展开集群、聚焦路径时使用短促、平滑的过渡；允许用户关闭动效和透视效果。若后续确实需要自由旋转视角，再单独评估交互式 3D 模式。
- 颜色读取项目主题 Token。当前界面同时存在蓝色主色和 dashboard 青绿色主色，节点/关系的语义色需要跟随所选界面风格与明暗主题映射；不可固定套用另一套荧光霓虹配色。
- 通过节点卡片层级、分组底色、边缘高光和关系线表达视觉质感，控制光效范围；默认视图保持克制，选中和悬停时再增强亮度、阴影和描边。
- 支持明暗主题、高对比度和 `prefers-reduced-motion`。颜色不能成为状态的唯一表达方式，审核状态还要显示文字/图标。

#### 图谱布局

- 默认采用稳定的分层布局：三层本体形成清晰泳道，领域/场景在泳道内聚类，业务语义居于中心，分析解释和映射治理显示其连接关系。
- 将跨场景桥接显示为醒目的弧形/跨区连线，并保留两端场景、契约状态和审核状态；候选、确认、驳回用线型、箭头和状态徽标共同表达。
- 大图按领域或场景折叠成集群摘要，显示节点数和待审核数；用户展开集群后再查看局部节点，避免首次打开渲染一整张密集大图。
- 保留确定性自动布局和用户拖动保存布局。重置布局只影响画布坐标，不改本体内容；切换筛选或版本时尽可能保持用户的空间上下文。
- 首期继续基于现有 React Flow，复用拖动、缩放、全屏、搜索定位和布局保存能力；先优化节点/连线/布局和筛选交互，不为了特效引入新图库。若后续规模或布局效果成为瓶颈，再对 G6 做独立 PoC。
- 先验证 React Flow 下的轴测布局、分层面板、弧形连线和视图切换是否能达到目标空间感；如需真实相机旋转/深度拾取，再对现有 G6 依赖做 3D PoC，比较可读性、性能、无障碍和维护成本后决定是否增加空间模式。

#### 节点、连线和交互

- 节点卡片至少显示类型图标/色标、名称、审核状态、定义摘要和来源/证据数量。指标卡片优先显示单位、聚合、粒度等关键口径；在低缩放级别自动简化卡片内容。
- 连线默认细而低对比；悬停或选中时显示关系名称和方向，选中对象时高亮其一跳邻居及路径，其余内容柔和淡出。选中的关键关系可以短暂显示流动光点，表示语义路径，不表示数据正在执行。
- 点击节点打开右侧详情面板，展示属性、关系、审核历史和证据；从证据可回到对应来源场景/文档。点击关系展示两端对象、方向、条件和来源。
- 搜索支持名称、别名、ID、来源场景和指标口径；命中后平滑定位并高亮。提供“全局概览”“按场景”“按领域”“来源追溯”视图，图层筛选与对象列表筛选联动。
- 将搜索、筛选、重置/适应视图、布局保存、全屏等操作放在统一工具栏；图例说明节点类型、关系类型和审核状态。小屏下详情面板改为抽屉，图例可折叠。
- 动效只服务于定位、展开、选中和路径追溯，不让所有节点持续呼吸或所有连线常驻流动；减少眩晕、干扰和大图性能开销。

### 5.6 版本与发布

版本列表展示修订作者、更新时间、生成方式、来源快照、验证状态、审核状态和发布状态。发布页按顺序展示技术检查、人工审核、来源快照一致性、快照构建、Neo4j 同步校验和激活结果。提供活动版本与目标版本的对象级 Diff；回退通过重新激活历史不可变快照完成，不改写历史修订。

## 6. 审核状态和发布规则

修订生命周期与对象审核状态分开保存，避免把技术状态和业务判断混在一个 `status` 字段中。

### 修订状态

建议：`draft`、`in_review`、`changes_requested`、`approved`、`ready`、`active`、`superseded`、`failed`。现有 `draft/ready/active/superseded/failed` 保持兼容；新增审核状态可先独立字段/事件计算，不要求一次性重写历史状态。

### 对象审核状态

建议：`candidate`、`in_review`、`confirmed`、`rejected`、`deprecated`。审核事件作用于稳定对象 ID 和对象内容指纹。发生属性、关系、证据或来源变化时，原审核事件仍保留，但不再满足当前指纹，需重新审核。

### 发布阻断规则

- 编译检查通过不能代替业务审核通过。
- 指标必须有可回溯的语义文档证据；缺证据或来源快照已变化时禁止审批/发布。
- 场景绑定进入运行时前必须经过确认，并指向存在的本体对象和来源场景快照。
- 跨场景关系只有 `confirmed` 且契约完整时才能进入运行时分析；候选、驳回和已废弃状态不可用。
- 规则和指标的审核要求可按风险等级配置；未审核对象不能以“已确认”状态进入活动快照。
- 修订级审批必须绑定 `content_hash`、编译器版本和来源快照集合。任一值改变都要求重审。
- 可配置四眼规则：开启后，创建/最后编辑该修订的用户不能批准或发布该修订；默认可关闭以兼容单管理员部署。
- 发布失败或 Neo4j 校验失败时，不切换活动版本；保留原因、同步状态和重试能力。Neo4j 已启用时必须通过同步校验；Neo4j 未启用时沿用现有 JSON 快照发布路径。

## 7. 数据与服务设计

### 7.1 数据库

复用 `ask_data_ontology_revision` 和 `ask_data_ontology_snapshot`，增加必要的修订审核元数据或从事件表聚合；新增统一追加写入的 `ask_data_ontology_event`，既记录对象/修订审核，也记录生成、编辑、发布、回退和同步等治理动作，至少包含：

```text
event_id, event_type, ontology_id, revision, target_type, target_id,
target_fingerprint, decision, comment, actor_id, created_at,
source_snapshot_ids, content_hash, metadata_json
```

事件不可更新或删除。当前审核状态由同一对象/指纹的最新有效审核事件推导；修订级审批也写入事件，并绑定当时内容哈希和来源快照。审核通过的 `ReviewRecord` 可在发布时编译进快照并投影到 Neo4j；关系库事件表是审计权威源。对历史修订采用增量兼容：旧版本默认显示“未记录审核”，不得自动标为已审核。

为保护人工工作，生成预览后应用结果应创建新修订或显式分支，并保留父修订、生成任务摘要和来源快照。不要在没有预览/确认的情况下覆盖含人工修改的现有草稿。

### 7.2 服务/API

在现有 `/api/v1/ask-data/ontology` 管理 API 上扩展，不改变当前快照运行时读取结构。建议新增或补强：

- `GET /workbench/status`：工作台待办、状态汇总和来源是否过期。
- `GET /revisions/{revision}/objects`：对象筛选、分页和审核状态。
- `GET /revisions/{revision}/objects/{object_id}/evidence`：来源、证据和定位信息。
- `POST /revisions/{revision}/reviews`：单对象/批量审核事件，附决定和意见。
- `POST /revisions/{revision}/reviews/exclude`：将对象从当前草稿排除，事务性清理可识别的关联引用并记录排除审计事件；不修改活动快照。
- `POST /revisions/{revision}/submit-review`：冻结当前内容并进入审核。
- `POST /revisions/{revision}/approve`：修订级审批，按内容哈希和来源快照写入批准记录。
- 发布端点增加服务端审核校验；请求需传 `expected_revision` / `content_hash` 防止并发和过期页面发布。
- `GET /revisions/{revision}/diff`：返回对象级变化及来源变化，保留原始文本 Diff。

错误码清晰区分：版本冲突、审核未完成、证据缺失、来源已过期、审批已失效、权限不足、图存储未就绪。写 API 维持现有 `admin` / `ask_data_admin` 后端授权检查；前端权限仅控制显示。

### 7.3 图投影

`OntologyGraph` 仍是运行时兼容结构。发布编译器将审核状态、来源证据和审核记录投影到三层 manifest；只有允许状态的对象会进入活动运行时投影。Neo4j 保存该不可变投影，不承载草稿状态迁移。

## 8. 分阶段实施

### 阶段 0：产品和数据契约

- 确认对象风险分级、审核规则、四眼模式开关和历史修订默认状态。
- 为实体、指标、规则、绑定和跨场景路径定义统一对象摘要、来源证据、指纹和 Diff 契约。
- 确认现有 `source_metric_refs`、`provenance`、场景快照字段如何映射到证据 UI。

交付：API/数据 DTO、状态转换图、审核规则表和页面原型。

### 阶段 1：可见性和生成保护

- 改造总览和版本列表，显示来源陈旧、验证状态和审核待办。
- 增加对象列表、筛选、对象详情侧栏和证据查看。
- 优先升级图谱画布：三层空间面板、领域/场景集群、聚焦邻居与路径、主题适配的节点/连线和来源详情；提供平面视图作为审核工作模式。
- 增加生成预览、对象级 Diff 和“创建新修订”流程，保护现有人工草稿。
- 保留现有 Markdown 编辑、图谱和桥接审核作为兼容入口。

交付：审核人员能看清本体对象、来源证据和生成变化；图谱具备分层聚类、状态表达、路径聚焦和主题适配；不改变运行时语义。

### 阶段 2：审核事件和服务端门禁

- 增加本体事件表、对象指纹和修订审批记录；处理旧版本和数据库兼容。
- 提供待审列表、确认/驳回/退回修改、审核意见和历史记录。
- 将桥接审核从仅编辑 Markdown 状态迁移为事件记录，同时双读/双写过渡一版，之后以审核事件为准。
- 发布 API 强制校验审核、内容哈希、来源快照和权限；UI 不可绕过。
- 可选开启四眼审批，并审计所有生成、编辑、审核、发布、回退和 Neo4j 重试操作。

交付：审核流程可追溯，未达规则的修订无法发布。

### 阶段 3：结构化编辑和质量闭环

- 增加实体、指标、分析规则和绑定的业务表单；Markdown 作为高级编辑/导入导出方式保留。
- 增加对象冲突检测、重复概念提示、缺失证据提示、场景版本变化影响分析。
- 记录发布后运行时召回的本体快照 ID 与使用对象；提供低命中/未绑定对象回看入口。
- 根据审核驳回原因优化生成提示和规则生成质量，不将模型置信度作为自动审批依据。

交付：从审核反馈反哺生成和映射质量。

## 9. 验收标准

### 功能

- 管理人员可以按对象类型、状态、来源和风险筛选待审项，并从对象详情直接查看来源证据。
- 生成前可以预览来源场景和对象级 Diff；生成不会静默覆盖已有人工修改。
- 每个审核决定有审核人、时间、意见、对象指纹和来源版本；历史事件不可被覆盖。
- 对象内容或来源变化后，原审批不会继续生效。
- 候选跨场景关系不能进入运行时；已确认桥接必须满足完整分析契约。
- 发布时服务端拒绝未审核、审核已失效或来源已过期的修订；Neo4j 已启用但未就绪时拒绝发布。任何失败都不改变当前活动快照；Neo4j 未启用时沿用 JSON 快照路径。
- 可查看当前活动版本、历史发布版本、对象级差异和回退目标。

### 图谱体验

- 初次打开时层级、空间远近、场景/领域集群和节点关系清晰；密集图可以逐层展开，不出现无法辨读的连线堆叠。
- 空间视图有明确但克制的立体层次；平面视图可一键切换，切换后对象位置、选中项和审核状态保持一致。
- 选中实体/指标能在画布上突出关联路径，并在详情面板看到定义、来源证据和审核状态。
- 候选、确认、驳回、废弃状态不依赖颜色单独区分；图谱主色适配 Datrix 当前界面主题及明暗模式。
- 缩放、搜索定位、集群展开、详情开合和布局保存操作顺畅；动效可关闭，图谱数据不因布局操作发生变化。
- 图谱在测试数据规模下保持可交互；大图通过聚类/局部展开控制渲染节点数，并提供可观察的加载状态。

### 安全与兼容

- 未登录请求返回 401；无管理权限调用本体管理/审核/发布 API 返回 403。
- 所有状态与权限检查在服务端实施；审核意见按普通文本处理，不执行 Markdown/HTML 内容。
- 旧快照读取、JSON 运行时召回、Neo4j 关闭模式和现有本体 Markdown 导入导出继续可用。
- 数据库升级是增量和幂等的；历史记录标为未记录审核，不误判为通过。

### 质量指标

- 活动指标来源证据覆盖率 100%。
- 活动场景绑定确认率 100%；活动跨场景路径确认率 100%。
- 所有活动对象均可追溯到本体修订和发布快照；所有审核事件可关联审核时的内容指纹。
- 通过试点业务人员审核若干次生成结果，记录单对象平均审核耗时、驳回原因分布和生成后人工修改率，作为后续优化基线。

## 10. 测试与发布策略

- 单元测试：对象指纹稳定性、审核状态转换、来源/内容变更导致审批失效、发布门禁和运行时过滤。
- API 测试：审核/批准/发布权限、并发修订冲突、重复提交幂等性、旧修订兼容、错误码。
- 前端验证：生成预览、对象筛选、证据面板、Diff、审核确认、编译错误和发布失败反馈；执行 ESLint 与静态导出构建。
- 集成验证：关系库迁移、Neo4j ready/active 转换、同步失败不切换活动版本、历史快照回退。
- 先在测试库和 Neo4j 关闭模式验证，再在启用 Neo4j 的环境验证；保留原工作台入口和历史 Markdown，确保升级可回退。

## 11. 关键决策建议

1. 保留现有 Markdown 与图结构作为兼容基础，先补足证据、审核事件和发布门禁，再逐步完善表单编辑。
2. 将“技术有效”和“业务可信”作为两条独立状态轴，不能因编译通过而自动审核。
3. 审核必须绑定内容指纹和来源版本；这比仅保存一个 `confirmed` 字符串更能防止过期审批。
4. 首期继续用 `admin` / `ask_data_admin` 管理权限。用审核事件完整记录责任；仅在组织确实要求职责分离时开启四眼门禁，避免先扩展成通用权限系统。
5. 图谱首期优先完成“2.5D 分层空间 + 聚类 + 路径聚焦 + 证据侧栏 + 主题适配”；把自由旋转的真实 3D 作为 PoC 评估项，不做自动旋转或持续粒子特效。
6. 治理首期优先完成“对象级证据核对 + 审核审计 + 发布门禁”，再扩展更复杂的可视化图编辑器。
